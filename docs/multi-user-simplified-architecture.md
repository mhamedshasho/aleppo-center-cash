# تقرير معماري مبسّط: مساحة عمل لشخصين

**المشروع:** Aleppo Center Cash
**الموجّه إلى:** مالك المشروع وDeepSeek
**المرحلة:** Round 4 — Multi-User Simplified
**الحالة:** تصميم فقط؛ لم يتم تعديل الكود أو إنشاء Backend

## 1. القرار

النظام المطلوب هو مساحة عمل واحدة لمحل واحد، يستخدمها شخصان فقط:

- **Owner:** صاحب المحل.
- **Member:** شريك واحد.

يستخدم الشخصان نفس الحسابات والدفعات، وتظهر التغييرات بين الجهازين عبر مزامنة فورية. لا يوجد E2EE، ولا Recovery keys، ولا Device keys، ولا Key epochs، ولا Zero-knowledge.

البنية المقترحة هي **Supabase Free + Auth + PostgreSQL + RLS + Realtime + Audit Log**. هذا يحقق المطلوب بأقل تعقيد وتكلفة، مع بقاء الحماية الأساسية في طبقة النقل والتخزين والصلاحيات.

## 2. ما الذي نحتفظ به وما الذي نحذفه

### نحتفظ به

- Supabase Free لطيار محدود.
- Email + Password عبر Supabase Auth.
- Workspace واحد.
- مستخدمان فقط.
- دورا Owner وMember.
- PostgreSQL كمصدر الحقيقة.
- RLS لعزل مساحة العمل.
- Realtime لتحديث الواجهات.
- سجل تدقيق خادمي.
- حل تعارض بسيط يعتمد على إصدار السجل.
- Local outbox بسيط لإعادة المحاولة عند انقطاع الشبكة.
- واجهة RTL ولهجة سورية.

### نحذف بالكامل

- E2EE.
- Recovery 2-of-3.
- مفاتيح الأجهزة.
- Key envelopes.
- Key epochs.
- libsignal أو أي بروتوكول تشفير رسائل.
- Zero-knowledge.
- نظام دعوات متعدد المستخدمين.
- أدوار Admin وGuest.
- نظام فرق أو عدة Workspaces.

## 3. البنية الخلفية

```text
تطبيق React RTL على جهاز Owner أو Member
              ↓
       Supabase Auth / JWT
              ↓
        PostgreSQL + RLS
              ↓
     Realtime + Audit Log
```

يكون Supabase هو مصدر الحقيقة عند الاتصال. يحتفظ التطبيق بنسخة محلية مؤقتة وطابور تغييرات صغير حتى لا تضيع العملية إذا انقطعت الشبكة أثناء الإرسال.

لا يكتب المتصفح مباشرة إلى كل الجداول الحساسة. تمر العمليات الأساسية عبر سياسات RLS ووظائف معاملاتية بسيطة، مثل:

- `create_payment`
- `update_account`
- `delete_account`
- `void_payment`
- `sync_pending_changes`

يمكن البدء بعمليات Postgres عادية محمية بـRLS، ثم استخدام RPC فقط للعمليات التي تحتاج فحص إصدار أو كتابة سجل تدقيق ضمن نفس المعاملة.

## 4. نموذج البيانات

| الجدول | الحقول الأساسية | الغرض |
|---|---|---|
| `workspace` | `id`, `name`, `timezone`, `created_at` | مساحة عمل واحدة للمحل. |
| `profiles` | `user_id`, `display_name` | اسم Owner وMember. |
| `workspace_members` | `workspace_id`, `user_id`, `role`, `active` | عضويتان فقط: Owner وMember. |
| `accounts` | `id`, `workspace_id`, `name`, `owner`, `version`, `is_archived` | حسابات الزبائن والموردين. |
| `payments` | `id`, `workspace_id`, `account_id`, `amount_minor`, `currency`, `type`, `date`, `version`, `created_by` | الدفعات والحركات. |
| `audit_log` | `id`, `workspace_id`, `user_id`, `action`, `entity`, `entity_id`, `summary`, `created_at` | سجل التغييرات. |
| `sync_events` | `id`, `workspace_id`, `entity`, `entity_id`, `version`, `created_at` | حدث خفيف لتحديث الأجهزة. |

تُخزن المبالغ كأرقام صحيحة مع العملة، وليس كأرقام عشرية عائمة. تكون كل التواريخ محفوظة بصيغة قياسية وتُعرض بالعربية السورية داخل الواجهة.

## 5. الصلاحيات

### Owner

يستطيع:

- تعديل الحسابات والدفعات.
- حذف الحسابات بعد تأكيد واضح.
- إضافة Member أو تعطيل حسابه.
- رؤية سجل التدقيق.
- تصدير واستيراد النسخ الاحتياطية.
- تغيير اسم المحل وإعداداته.

### Member

يستطيع:

- رؤية الحسابات والدفعات.
- إضافة دفعات وتعديلها حسب سياسة المحل.
- تعديل بيانات الحساب الأساسية.
- رؤية التغييرات المشتركة.

لا يستطيع Member:

- حذف Workspace.
- تغيير Owner.
- إضافة أعضاء آخرين.
- تغيير الصلاحيات.
- حذف سجل التدقيق.
- تنفيذ حذف جماعي دون تأكيد وسياسة واضحة.

لأن النظام يحتوي على شخصين فقط، لا نحتاج إلى نظام دعوات عام. ينشئ Owner حساب Member مرة واحدة أو يضيفه من شاشة إعداد بسيطة. لا يجب استخدام حساب واحد مشترك؛ لكل شخص بريد وكلمة مرور مستقلان حتى يبقى سجل التدقيق صحيحاً.

## 6. Auth

يستخدم النظام Email + Password عبر Supabase Auth. يجب تطبيق ما يلي:

- كلمة مرور قوية وطويلة.
- TLS لكل الاتصالات.
- جلسات منتهية الصلاحية وتدوير عند تسجيل الدخول.
- Rate limiting لمحاولات الدخول.
- عدم إظهار ما إذا كان البريد موجوداً في رسائل الاسترداد.
- تفعيل MFA لحساب Owner إذا كان متاحاً.
- إبقاء مفاتيح Supabase السرية خارج المتصفح.

لا يوجد E2EE. هذا يعني أن Supabase يستطيع قراءة البيانات عند وجود صلاحية خادمية أو إدارية مناسبة، ولذلك يجب تقليل وصول لوحة Supabase إلى شخص تقني موثوق فقط.

## 7. RLS والعزل

رغم وجود Workspace واحد فقط، يجب تطبيق RLS من البداية حتى لا تصبح البيانات مكشوفة إذا توسع النظام لاحقاً.

القاعدة الأساسية لكل جدول هي:

```text
المستخدم يستطيع القراءة أو التعديل فقط إذا كان عضواً فعالاً في workspace_id.
```

تكتب سياسات منفصلة للقراءة والإضافة والتعديل والحذف. يحظر على Member تغيير `workspace_id` أو `created_by` أو `audit_log`. لا يوضع `service_role` في React أو أي ملف يصل إلى المتصفح.

يجب اختبار حالتين لكل سياسة:

1. Owner أو Member مصرح له يرى ويعدل البيانات الصحيحة.
2. مستخدم غير عضو أو عضو مع عملية غير مسموحة يُرفض طلبه.

## 8. Real-time sync

عند إضافة أو تعديل دفعة، يكتب السيرفر التغيير ثم ينشر حدثاً خفيفاً مثل:

```json
{
  "workspace_id": "…",
  "entity": "payment",
  "entity_id": "…",
  "version": 4,
  "action": "updated"
}
```

لا يحتاج Realtime إلى إرسال كل حالة التطبيق. يكفي أن يتلقى الجهاز الآخر الحدث ثم يجلب الصف المحدث عبر استعلام RLS مصرح به. هذا يقلل التسريب ويجعل البيانات الخادمية هي المرجع.

عند فتح التطبيق أو عودة الاتصال:

1. يجلب الجهاز آخر نسخة من الحسابات والدفعات.
2. يقارن آخر `version` محلية مع الخادم.
3. يرسل العمليات المعلقة بترتيبها.
4. يطلب التغييرات التي حدثت بعد آخر cursor.
5. يعرض أي تعارض بدلاً من استبداله بصمت.

## 9. حل التعارضات المبسط

لا نحتاج CRDT أو نظام تعارض معقد لشخصين فقط. نستخدم optimistic concurrency بإصدار لكل حساب ودفعة.

عند تعديل سجل:

1. يرسل العميل `entity_id` و`expected_version`.
2. يقبل السيرفر التعديل فقط إذا كان الإصدار ما زال مطابقاً.
3. يرفع السيرفر الإصدار بعد نجاح التعديل.
4. إذا تغير السجل من الجهاز الآخر، يرجع Conflict.
5. تعرض الواجهة القيمتين والفاعل والوقت.
6. يختار المستخدم الاحتفاظ بتعديله أو استخدام التعديل الآخر.

بالنسبة للدفعات، لا نعتمد `last-write-wins` للمبلغ أو النوع أو الحساب. إذا كانت الدفعة بحاجة إلى تصحيح، يسجل التصحيح أو الإبطال في Audit Log. يمكن السماح بدمج تلقائي لحقول غير حساسة مثل اسم الحساب إذا لم يتغير الحقل نفسه على الجهاز الآخر.

## 10. Audit Log

ينشئ السيرفر Audit Log لكل عملية مهمة:

- تسجيل الدخول والخروج.
- إضافة أو تعديل أو حذف حساب.
- إضافة أو تعديل أو حذف دفعة.
- استيراد أو تصدير نسخة.
- تغيير Member.
- تعارض أو فشل مزامنة.
- تغيير إعدادات Workspace.

كل حدث يحتوي على المستخدم، العملية، الكيان، المعرّف، ملخصاً قصيراً، والوقت الخادمي. لا يُسمح للمستخدمين بحذف السجل أو تعديله.

يعرض Owner السجل الكامل. يمكن لـMember رؤية نشاط مساحة العمل الضروري، من دون صلاحية حذف السجل.

## 11. الخصوصية

هذا التصميم ليس E2EE. البيانات محمية عبر:

- HTTPS/TLS أثناء النقل.
- تشفير التخزين لدى Supabase حسب إعدادات المنصة.
- RLS وعزل العضوية.
- كلمات مرور وجلسات آمنة.
- وصول محدود إلى Dashboard.
- عدم استخدام Analytics أو Trackers داخل المساحة الخاصة.
- عدم وضع بيانات مالية كاملة في Push Notifications.
- تصدير واستيراد محلي مع تحذير أن الملفات غير مشفرة ما لم يحمِها المستخدم.

يجب أن تكون سياسة الخصوصية صريحة: **السيرفر يستضيف البيانات ويمكنه قراءتها ضمن صلاحيات الإدارة والبنية، وهذا النظام ليس E2EE.**

## 12. Free tier

Supabase Free مناسب لحجم مستخدمين اثنين وWorkspace واحد. الحدود الحالية المعروفة تشمل 500 MB لقاعدة البيانات، و1 GB للتخزين، وحدوداً سخية نسبياً لـAuth وRealtime بالنسبة لهذا الاستخدام.

لكن يجب قبول المخاطر التالية:

- قد يتوقف مشروع Free بعد قلة النشاط.
- لا توجد نسخ احتياطية تلقائية مناسبة للاعتماد عليها وحدها.
- قد تحتاج رسائل Auth إلى SMTP مخصص بسبب حد الرسائل المدمج.
- يجب مراقبة التخزين والخروج.

قبل استخدام بيانات تشغيلية مهمة، ينفذ الفريق:

1. تصدير JSON دوري.
2. نسخة منفصلة من البيانات الأساسية.
3. اختبار Restore فعلي.
4. مراقبة حالة المشروع والحصص.
5. خطة واضحة إذا توقف المشروع أو امتلأت الحصة.

## 13. الجدول الزمني الجديد

### الأسبوع الأول: Backend وAuth

إنشاء Supabase Project، والجداول، وAuth، وWorkspace، وعضويتين، وسياسات RLS، وبيانات تجريبية.

**نتيجة الأسبوع:** Owner وMember يستطيعان الدخول ورؤية نفس الحسابات مع عزل صحيح.

### الأسبوع الثاني: Realtime والتدقيق

إضافة عمليات الحسابات والدفعات، Realtime، Audit Log، optimistic versioning، ورسائل التعارض باللهجة السورية.

**نتيجة الأسبوع:** تعديل من جهاز يظهر على الجهاز الآخر، والتعارض لا يضيع بصمت.

### الأسبوع الثالث: الاختبار والتسليم

اختبار جهازين، انقطاع الشبكة، duplicate submission، حذف وتعديل الحسابات، صلاحيات Member، الاستيراد والتصدير، RTL، PWA، TypeScript وProduction Build.

**المدة الكاملة:** **2–3 أسابيع** لفريق يعرف البنية الحالية، بشرط عدم إضافة E2EE أو Admin roles أو عدة Workspaces أو نظام دعوات عام.

## 14. المخاطر المقبولة

| الخطر | المعالجة البسيطة |
|---|---|
| السيرفر يستطيع قراءة البيانات | إعلان واضح أن النظام ليس E2EE، وتقليل وصول Dashboard. |
| توقف Free | Export دوري وRestore Drill، وعدم اعتباره Backup إنتاجياً. |
| تعارض تعديلين | Version check ورسالة اختيار واضحة، لا overwrite صامت. |
| حذف خاطئ | Confirm، Audit Log، ويفضل Archive قبل الحذف النهائي. |
| فقدان الشبكة | Local outbox وإعادة إرسال idempotent. |
| تسريب كلمة مرور Owner | MFA، جلسات منتهية، rate limiting، وتنبيهات دخول. |
| توسع المتطلبات لاحقاً | إبقاء `workspace_id` وRLS من البداية. |

## 15. القرار النهائي المقترح

اعتماد بنية بسيطة من **Supabase Free، Email + Password، Workspace واحد، Owner وMember، RLS، Realtime، Audit Log، وVersion-based conflict resolution**.

لا نضيف E2EE أو Recovery أو Device keys أو نظام فرق أو دعوات عامة. لا نحتاج إلى libsignal أو CRDT أو key management. هذا يعطي أقل تكلفة وأسرع طريق إلى تطبيق مشترك يعمل بشكل صحيح لشخصين.

الشرط الأساسي هو أن يوافق المالك صراحة على أن السيرفر يستطيع قراءة البيانات وأن Free لا يضمن التوافر والنسخ الاحتياطي الدائمين. إذا تغير عدد المستخدمين أو ظهرت حاجة إلى سرية ضد السيرفر، يعاد فتح القرار المعماري في مرحلة مستقلة.
