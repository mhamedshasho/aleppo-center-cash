# تقرير معماري: مساحة عمل مشتركة متعددة المستخدمين

**المشروع:** Aleppo Center Cash
**المرحلة:** Round 4 — Multi-User Architecture
**الموجّه إلى:** DeepSeek
**الحالة:** تصميم وتقييم فقط؛ لم يتم تعديل الكود أو إضافة Backend

> هذا التقرير يصف بنية مقترحة لمحل واحد يعمل فيه 3–5 شركاء على نفس البيانات. وهو تقرير هندسي وتشغيلي، وليس موافقة قانونية أو تدقيقاً أمنياً نهائياً.

## 1. القرار المقترح

الطلب الجديد ليس مزامنة عادية بين جهازين، بل **Shared Workspace** حقيقي. لذلك يحتاج التطبيق إلى هوية مستخدمين، ومساحة عمل مشتركة، وعضويات وصلاحيات، ودعوات، وقاعدة بيانات مركزية، ومزامنة فورية، وحل تعارضات، وسجل تدقيق، وإشعارات.

أوصي باستخدام **Supabase** كبنية أولية للطيار، مع PostgreSQL كمصدر الحقيقة، وSupabase Auth للهوية، وRow Level Security لعزل البيانات، وStorage خاص للمرفقات، وEdge Functions للعمليات الخادمية المحدودة، وRealtime كقناة تسريع لا كمصدر الحقيقة.

يصلح Supabase Free لطيار محدود من 3–5 شركاء من ناحية السعة. لكن الخطة المجانية ليست خطة إنتاج آمنة لسجل نقدي دائم، لأنها قد توقف المشروع بعد سبعة أيام من قلة النشاط، ولا توفر نسخاً احتياطية تلقائية. لذلك يكون القرار المقترح هو:

1. **Free Project واحد** لطيار مضبوط ببيانات محدودة.
2. **نسخ وتصدير واستعادة مستقلة** منذ اليوم الأول.
3. الانتقال إلى **Pro أو بديل مدار** قبل اعتماد النظام كسجل مالي تشغيلي دائم.
4. تأجيل E2EE إلى مرحلة منفصلة بعد مراجعة بروتوكول التشفير والاسترداد.

## 2. مبادئ التصميم

يبقى التطبيق Arabic RTL وLocal-first من ناحية تجربة الاستخدام. يستطيع المستخدم العمل محلياً عند انقطاع الشبكة، لكن يصبح السيرفر مصدر الحقيقة عند المزامنة. لا يجوز اعتبار WebSocket أو Realtime بديلاً عن المعاملة الخادمية أو سجل التدقيق.

كل مساحة عمل معزولة عن غيرها. كل كتابة تمر عبر صلاحيات خادمية، والتحقق من الإصدار، ومفتاح idempotency، وسجل تدقيق، ثم تحديث الإسقاط الحالي وإشعار المزامنة داخل معاملة واحدة.

الدفعات حقائق مالية. لا يجوز تعديل المبلغ أو الاتجاه أو الحساب بصمت. التصحيح يكون عبر إبطال أو حدث تصحيح مرتبط بالدفعة الأصلية، مع الاحتفاظ بالأثر السابق.

لا توضع أسرار Supabase أو مفاتيح `service_role` في المتصفح. ويجب أن تكون كل جداول البيانات والمرفقات محمية بـRLS وسياسات رفض صريحة، وليس بسياسات السماح فقط.

## 3. البنية الخلفية المقترحة

تتكون البنية من تطبيق React محلي، وSupabase Auth، وPostgreSQL، وطبقة RPC معاملاتية، وRealtime خاص، وStorage خاص، وEdge Functions محدودة، وطابور أوامر محلي.

التدفق الأساسي هو:

```text
تطبيق RTL محلي
    ↓
Supabase Auth / JWT
    ↓
RPC محمي بالصلاحيات وRLS
    ↓
PostgreSQL: projections + ledger_events + outboxes
    ↓
Realtime Broadcast خاص + إشعارات
```

لا يكتب العميل مباشرة إلى الجداول المالية. بدلاً من ذلك يستدعي أوامر مثل:

- `create_payment`
- `update_account`
- `void_payment`
- `apply_sync_batch`
- `invite_member`
- `change_member_role`

تتحقق كل وظيفة من العضوية والدور، وصحة البيانات، والإصدار المتوقع، وidempotency، ثم تكتب النتيجة وسجل التدقيق وحدث المزامنة ضمن معاملة واحدة.

### حدود Supabase Free ذات الصلة

بحسب وثائق Supabase الحالية، توفر الخطة المجانية تقريباً **50,000 مستخدم نشط شهرياً، و500 MB لقاعدة البيانات، و1 GB للتخزين، و5 GB خروج بيانات غير مخزنة مؤقتاً، و5 GB خروج مخزن مؤقتاً، و2 مليون رسالة Realtime شهرياً، و200 اتصال Realtime متزامن، و500,000 استدعاء Edge Functions شهرياً**. هذه السعة أكثر من كافية لطيار 3–5 شركاء.

لكن توجد قيود تشغيلية مهمة:

- المشاريع المجانية قد تتوقف بعد سبعة أيام من انخفاض النشاط.
- لا توجد نسخ احتياطية تلقائية كافية للاعتماد عليها كسجل مالي دائم.
- مرسل البريد المدمج في Auth محدود إلى رسالتين في الساعة؛ لذلك يلزم SMTP مخصص للدعوات وإعادة التعيين.
- التخزين والخروج والنسخ الاحتياطي تحتاج مراقبة منفصلة.
- أعضاء لوحة Supabase في Free وPro ليسوا محصورين بمشروع واحد؛ لذلك لا يجب منح الشركاء وصول Dashboard.

## 4. نموذج البيانات

يجب أن يحمل كل جدول نطاقي `workspace_id`. تُخزن الأموال كأعداد صحيحة بوحدات العملة الصغرى مع رمز عملة واضح، ولا تستخدم الفاصلة العائمة. تُحفظ التواريخ بصيغة UTC وتُعرض حسب المنطقة الزمنية لمساحة العمل.

| الجدول | الحقول الأساسية | الملاحظات الأمنية والتشغيلية |
|---|---|---|
| `workspaces` | `id`, `name`, `currency`, `timezone`, `created_at` | يمثل المحل أو المركز النقدي. |
| `profiles` | `user_id`, `display_name`, `locale` | بيانات المستخدم الدنيا المرتبطة بـAuth. |
| `workspace_members` | `workspace_id`, `user_id`, `role`, `active`, `joined_at`, `removed_at` | فريد لكل مستخدم داخل مساحة العمل، ومفهرس لاستخدام RLS. |
| `invitations` | `id`, `workspace_id`, `email_hash`, `role`, `token_hash`, `expires_at`, `accepted_at`, `revoked_at` | رمز أحادي الاستخدام مخزن كـhash. |
| `accounts` | `id`, `workspace_id`, `name`, `owner`, `version`, `is_archived` | الأرشفة أفضل من الحذف المباشر. |
| `payments` | `id`, `workspace_id`, `account_id`, `direction`, `amount_minor`, `currency`, `occurred_at`, `status`, `version`, `created_by`, `replaces_payment_id` | التصحيح والإبطال أحداث، وليس overwrite صامتاً. |
| `ledger_events` | `event_id`, `workspace_id`, `entity_id`, `event_type`, `entity_version`, `actor_user_id`, `device_id`, `client_event_id`, `idempotency_key`, `payload`, `global_seq` | append-only ولا يسمح للعميل بتعديله أو حذفه. |
| `realtime_outbox` | `id`, `workspace_id`, `event_id`, `safe_envelope`, `published_at` | يحمل IDs وإصدارات وتسلسلاً فقط، لا الملاحظات أو البيانات الحساسة. |
| `notification_outbox` | `event_id`, `recipient_user_id`, `kind`, `status`, `attempts`, `delivered_at` | ينشأ داخل نفس معاملة الحدث ويُسلّم بشكل idempotent. |
| `audit_events` | `workspace_id`, `actor`, `action`, `target`, `redacted_diff`, `source`, `request_id`, `occurred_at` | مخصص للتغييرات والصلاحيات والتصدير والأمان. |
| `devices` | `user_id`, `label`, `public_key_or_ref`, `last_seen_at`, `revoked_at` | مطلوب لإدارة الأجهزة ومرحلة E2EE المحتملة. |

الفهارس المهمة هي `(workspace_id, global_seq)`، و`(workspace_id, entity_id, entity_version)`، وفهارس العضوية، وفهارس طوابير الإشعارات. يجب وضع قيود فريدة على `(workspace_id, idempotency_key)` وعلى `(workspace_id, device_id, client_event_id)`.

## 5. المستخدمون والأدوار

### Owner

يمتلك مساحة العمل، ويدعو Admin وMember، ويدير الأدوار، ويطّلع على سجل التدقيق الكامل، ويوافق على التصدير الشامل، وإعدادات الاسترداد، وإزالة الشركاء. العمليات الحساسة تحتاج إعادة مصادقة حديثة، ويفضل موافقة Owner ثانٍ.

### Admin

يدير الحسابات والدفعات، ويدعو Members، ويتابع التعارضات والإشعارات. لا يزيل Owner، ولا يغير سياسة الاسترداد، ولا ينفذ تصديراً كاملاً أو يرفع عضواً إلى Owner دون موافقة مالك.

### Member

يقرأ البيانات المسموحة، ويضيف الدفعات، ويتابع مهامه وتعارضاته، ويزامن جهازه. لا يدير المستخدمين أو الأدوار، ولا يعدل حقيقة مالية بصمت، ولا يرى سجل التدقيق الكامل.

هذه أدوار داخل التطبيق وليست أدوار لوحة Supabase. وصول Dashboard يقتصر على مسؤول تقني واحد أو اثنين مع MFA، بينما يستخدم الشركاء حسابات التطبيق فقط.

## 6. المصادقة والدعوات

المسار المفضل على المدى الطويل هو **Passkeys/WebAuthn** لأنها تربط الاعتماد بنطاق الموقع وتقاوم التصيد أكثر من كلمات المرور والروابط السحرية وOTP. لكن يجب اختبار دعم الأجهزة والاسترداد قبل اعتمادها كمسار وحيد.

للطـيار، يمكن استخدام كلمة مرور قوية مع جلسات آمنة وrate limiting. يجب قبول Unicode والمسافات المناسبة للمستخدم العربي، وتجنب فرض تغيير دوري اعتباطي، واستخدام آلية hash قوية داخل طبقة الهوية.

لا يُنصح باستخدام SMS كوسيلة الاسترداد الوحيدة بسبب SIM-swap وإعادة تدوير الأرقام. الروابط السحرية تكون أحادية الاستخدام وقصيرة العمر، ولا تستخدم لتأكيد تغيير دور أو تصدير شامل أو استرداد مفتاح.

### تدفق الدعوة

1. ينشئ Owner أو Admin دعوة محددة بالبريد والدور ومدة انتهاء.
2. يخزن السيرفر hash للرمز، ولا يخزن الرمز الصريح.
3. ترسل الدعوة عبر SMTP مخصص.
4. يفتح المدعو الرابط ويؤكد الحساب داخل المتصفح.
5. يتحقق السيرفر من الرمز والبريد والحالة داخل معاملة.
6. تنشأ العضوية، ويسجل حدث تدقيق، ويرسل إشعار للشركاء.
7. لا يمكن لرابط الدعوة أن يرفع صلاحيات المدعو عن الدور الذي حدده صاحب الدعوة.

إضافة جهاز جديد، تغيير دور، إزالة شريك، تغيير الاسترداد، أو تصدير كامل تحتاج re-auth حديثة وإشعاراً للشركاء.

## 7. RLS والعزل

يجب تفعيل RLS على كل جدول مكشوف، مع سياسات منفصلة للقراءة والإضافة والتعديل والحذف. القاعدة العامة هي وجود عضوية فعالة لمساحة العمل مع فحص الدور المناسب.

ينطبق ذلك أيضاً على `storage.objects`. تكون المرفقات في Buckets خاصة، ولا يرسل التطبيق روابط عامة. يجب اختبار حالات السماح والرفض لكل سياسة، وفحص Views وFunctions بعناية، لأن وجود Policy لا يلغي Grants تلقائياً.

تبقى مفاتيح `service_role` وSMTP وأسرار Webhooks في Edge Functions أو بيئة خادمية. لا يسمح لأي عميل بتعديل `workspace_id` أو `ledger_events` أو `audit_events` مباشرة.

## 8. المزامنة الفورية والعمل دون اتصال

يحتفظ العميل بطابور أوامر محلي داخل IndexedDB أو طبقة تخزين مشفرة قدر الإمكان. يحتوي كل أمر على:

```text
client_event_id
idempotency_key
device_id
workspace_id
command
entity_id
expected_version
payload
created_at
state
attempts
```

يمكن للواجهة عرض التعديل فوراً بحالة «قيد المزامنة». عند عودة الاتصال، يرسل العميل دفعات محدودة. لا يحذف الأمر إلا بعد قبول خادمي دائم أو استجابة idempotent. إذا فشل كيان واحد، يتوقف مساره فقط وتستمر الكيانات المستقلة.

يكون ترتيب السيرفر هو canonical order. يحتفظ العميل بـ`last_global_seq`، ويزيل تكرار `event_id`، ولا يطبق حدثاً أقدم من `entity_version` الحالية. بعد الاشتراك أو إعادة الاتصال، ينفذ Catch-up paginated للأحداث بعد المؤشر. هذا ضروري لأن Realtime قد يتأخر أو ينقطع أو تصل الرسائل بترتيب مختلف.

التصميم المستهدف هو **Private Supabase Broadcast** مع RLS على القناة، يحمل IDs والنوع والإصدار والتسلسل فقط. يجلب العميل الصف الكامل عبر استعلام مصرح به. يمكن استخدام Postgres Changes في طيار صغير مفلتر، لكنه لا يكون المصدر الوحيد للحقيقة.

## 9. حل التعارضات

لا تستخدم سياسة `last-write-wins` للدفعات. الوقت على جهاز العميل ليس مصدراً موثوقاً للترتيب.

كل تعديل على كيان موجود يحمل `expected_version`. يحدّث السيرفر الصف فقط إذا بقي الإصدار كما هو. إذا لم يتغير أي صف، يعيد Conflict Response تحتوي على الإصدار الخادمي والبيانات الحالية والإصدار الذي عدله العميل.

يمكن دمج حقول الحساب المستقلة تلقائياً إذا ثبت اختلافها عن بعضها. أما المبلغ، والاتجاه، والحساب، والإبطال، فتحتاج قراراً بشرياً. تعرض الواجهة بالعربية:

- «احتفظ بتعديلي»
- «استخدم التعديل الآخر»
- «راجع القيمتين»

تصحيح دفعة متعارضة يكون عبر حدث جديد، مثل `payment_voided` أو `payment_corrected`، مع حفظ القيمتين وسجل الفاعل والوقت.

## 10. التدقيق والإشعارات

ينشئ الخادم سجل التدقيق، لا العميل. يسجل السجل:

- تسجيل الدخول وتغييرات الجلسات والأجهزة.
- الدعوات والعضويات والأدوار.
- إنشاء الدفعة وإبطالها وتصحيحها.
- اكتشاف التعارض وحله.
- التصدير والاستعادة والحذف.
- وصول الدعم أو العمليات الحساسة.

يجب ألا يسجل كلمات المرور أو الرموز أو محتوى مالي كامل في سجلات عامة. يقتصر عرض التدقيق الكامل على Owner، ويظهر لـAdmin سجل تشغيلي محدود.

تدخل الإشعارات عبر `notification_outbox` ضمن نفس المعاملة التي تنشئ الحدث. ترسل إشعارات للدعوات، وتغييرات الصلاحيات، والتعارضات، والإبطال والتصحيح، وإضافة جهاز جديد. تكون معاينة الإشعار مقتصدة، مثل «هناك تحديث جديد في الحسابات»، ولا تعرض مبلغاً أو ملاحظة إلا بعد تحقق الصلاحية.

## 11. تقييم E2EE

E2EE ممكن، لكنه ليس إضافة بسيطة. عند تطبيقه، ينشئ كل جهاز مفتاح هوية، وتنشئ مساحة العمل مفتاح محتوى، وتشفّر الدفعات على الجهاز باستخدام AEAD، ثم يغلّف مفتاح المحتوى لكل جهاز عضو بمفتاحه العام.

هذا يمنع السيرفر من قراءة السجل، لكنه يحد من البحث والتقارير والإشعارات الخادمية. كما يجعل الاسترداد أصعب: إذا فقد كل الشركاء مفاتيحهم، قد تضيع البيانات نهائياً.

لذلك لا أوصي بإطلاق E2EE في أول نسخة متعددة المستخدمين. يبدأ الطيار بتشفير النقل والتخزين، وRLS، وتشفير محلي، وسجلات تدقيق، ونسخ احتياطية محمية. تفتح E2EE كمرحلة لاحقة بعد:

1. تحديد نموذج التهديد.
2. اختيار مكتبة وبروتوكول مراجع، لا تشفير مخصص.
3. تصميم توزيع وتدوير وإبطال المفاتيح.
4. تحديد سياسة الاسترداد.
5. اختبار فقد الجهاز وإزالة الشريك.
6. مراجعة مستقلة لتصميم التشفير.

إذا تم اختيار استرداد محكوم بالشركاء، يمكن استخدام سياسة 2 من 3 أمناء، مع مهلة تبريد 24 ساعة وإشعار وتدوير مفتاح. لكن هذا يعني وجود جهة استرداد موثوقة، فلا يصح وصف النظام بأنه Zero-knowledge ضد هؤلاء الأمناء.

## 12. الخصوصية وGDPR

قد ينطبق GDPR إذا كانت الشركة داخل الاتحاد الأوروبي، أو إذا عرضت الخدمة على أشخاص في الاتحاد، حتى لو كانت الخدمة مجانية، أو راقبت سلوكهم هناك. مجرد إمكانية الوصول من أوروبا لا تكفي وحدها. لذلك يمكن أن يبدأ الطيار بشركاء مسمّين في سوريا فقط، من دون تسويق أو onboarding للاتحاد، مع إعادة التقييم قبل التوسع.

عادة يكون صاحب المحل أو الشركة المتحكمة في الغرض من بيانات العملاء والموردين هو Controller، بينما تكون Aleppo Center Cash Processor إذا عالجت البيانات وفق تعليمات الشريك. تصبح المنصة Controller مستقلاً لأنشطة الحساب والدعم والأمن والرسائل التي تحدد غرضها بنفسها.

قبل الإطلاق الحقيقي يجب إعداد:

- خريطة تدفق بيانات.
- قائمة بالموردين الفرعيين والمناطق والنسخ والدعم.
- سياسة احتفاظ وحذف.
- تصدير كامل للمستأجر.
- مسار لطلبات الوصول والتصحيح والحذف.
- DPA عند انطباق GDPR.
- خطة استجابة للحوادث.
- مراجعة لمكان البيانات والنسخ الاحتياطية.

يجب فصل البيانات المحاسبية التي يلزم الاحتفاظ بها قانونياً عن بيانات الحساب والدعم وسجلات الأمن والنسخ الدوارة. لا يعني زر حذف الحساب أن كل نسخة احتياطية تختفي فوراً؛ يجب توثيق المدة وآلية انتهاء النسخ.

| إعداد Supabase وAuth وRLS | 1–2 أسبوع |
| نموذج Workspace والعضويات والدعوات | 1 أسبوع |
| RPC والـidempotency وسجل التدقيق | 1–2 أسبوع |
| Outbox والمزامنة وإعادة الاتصال | 1–2 أسبوع |
| تعارضات الدفعات وواجهة RTL | 1–2 أسبوع |
| الإشعارات والمراجعة الأمنية | 1 أسبوع |
| اختبارات الخصوصية والاستعادة وPWA | 1 أسبوع |
| **إجمالي هندسي واقعي** | **6–10 أسابيع** |

هذه مدة تقديرية لفريق صغير مع أساس التطبيق الحالي، وليست التزاماً. E2EE، وPasskeys، وتكامل SMTP، ومراجعة قانونية مستقلة يمكن أن تضيف أسابيع أخرى.

Free مناسب للطيار، لكن لا ينبغي اعتبار الكلفة صفرية عند احتساب SMTP والنسخ المستقلة والمراجعة القانونية. يبدأ Supabase Pro من نحو 25 دولاراً شهرياً وفق الأسعار الحالية، مع اختلاف التكلفة النهائية حسب الاستخدام والإضافات. أما المراجعة القانونية فليست سعراً ثابتاً؛ ينبغي أخذ عرض محلي قبل التوسع.

## 14. المخاطر وبوابات الإطلاق

| الخطر | المعالجة | بوابة الإطلاق |
|---|---|---|
| خطأ RLS أو تسريب Tenant | سياسات RLS، اختبارات deny، منع service key في المتصفح | لا دعوات قبل مراجعة العزل |
| فقدان بيانات بسبب Free | Export وBackup مستقل واختبار Restore | لا تشغيل مالي دائم على Free فقط |
| تعارض مالي صامت | Versions، idempotency، void/correction | اختبار جهازين على نفس الدفعة |
| جهاز أو شريك مخترق | إدارة أجهزة، إبطال جلسات، إشعارات، حدود تصدير | تمرين إزالة جهاز وفقده |
| اعتماد البريد | SMTP مخصص ومراقب | اختبار الدعوات وإعادة التعيين |
| نقل دولي أو GDPR | Data map وDPA ومراجعة مناطق وموردين | لا EU onboarding قبل الإغلاق القانوني |
| E2EE غير قابل للاسترداد | Recovery policy ومراجعة تشفير | لا إعلان E2EE قبل مراجعة مستقلة |

## 15. الجدول الزمني المقترح

### الأسبوع 0–1: تثبيت النطاق

تأكيد أن الطيار لمحل واحد و3–5 شركاء، تحديد العملات والمنطقة الزمنية، اختيار منطقة Supabase، تعريف الأدوار، ووضع خريطة البيانات والاحتفاظ.

**بوابة G0:** هل يوجد مستخدم أو شريك أو استهداف داخل الاتحاد الأوروبي؟ إذا نعم، يبدأ التقييم القانوني قبل onboarding.

### الأسبوع 1–2: الأساس الخادمي

إنشاء Workspace وProfiles وMemberships، كتابة RLS، إعداد Auth وSMTP، وتثبيت الدعوات والصلاحيات.

**بوابة G1:** نجاح اختبارات allow/deny وعدم وجود أسرار في العميل.

### الأسبوع 3–4: الكتابة والمزامنة

تنفيذ RPC، وledger events، وidempotency، وversions، وlocal outbox، وcatch-up، وRealtime الخاص.

**بوابة G2:** نجاح اختبار offline، وإعادة الاتصال، والتكرار، وتحديثين متزامنين.

### الأسبوع 4–6: الطيار

إضافة حل التعارضات، والتدقيق، والإشعارات، والتصدير، والاستعادة، وإدارة الأجهزة، واختبارات RTL وPWA.

**بوابة G3:** لا توجد تعارضات مالية صامتة، وكل عملية حساسة مسجلة وقابلة للتصدير.

### الأسبوع 6–10: التوسع

قرار Pro أو بديل، مراجعة أمنية مستقلة، مراجعة قانونية عند الحاجة، اختبار الاستعادة، وتمرين حادث. يبدأ بحث E2EE فقط بعد إغلاق المخاطر الأساسية.

## 16. القرارات المطلوبة من المالك

1. اعتماد Supabase لطيار محدود أم اختيار Backend آخر.
2. السماح بإنشاء مشروع Free واحد مع قبول مخاطر التوقف والنسخ، أو اعتماد Pro/Backup مستقل منذ البداية.
3. اعتماد أدوار Owner وAdmin وMember.
4. اختيار Email/Password مع SMTP، أو بدء دمج Passkeys.
5. اعتماد سياسة التصحيح والإبطال بدلاً من تعديل الدفعة بصمت.
6. تحديد ما إذا كان الطيار محصوراً بشركاء سوريا المحليين.
7. تأجيل E2EE إلى Phase 2، أو تخصيص مراجعة تشفير مستقلة قبل أي وعد تسويقي.
8. تعيين مالك تشغيلي للنسخ الاحتياطي والحوادث والخصوصية.

## التوصية النهائية لـDeepSeek

نبدأ بتصميم **Supabase + PostgreSQL + Auth + RLS + RPC + append-only events + local outbox + private Realtime**، لكن لا نبدأ التنفيذ قبل موافقة المالك على بوابات G0 وG1. لا نستخدم last-write-wins للدفعات، ولا نعطي الشركاء وصول Dashboard، ولا نعلن E2EE في النسخة الأولى.

الطيار المجاني ممكن تقنياً، لكنه يحتاج نسخاً مستقلة واختبار استعادة قبل الوثوق به. أما الوصول من أوروبا أو تقديم E2EE، فهما قراران منفصلان يحتاجان مراجعة خصوصية وأمنية وقانونية.
